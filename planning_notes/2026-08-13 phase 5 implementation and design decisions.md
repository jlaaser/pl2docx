# pl2docx: Phase 5 Implementation and Design Decisions

Session handoff note. Phase 5 (subphases 1-3) is now **complete** — the tool can
render a real assessment end-to-end, including questions whose only content is a
static diagram (SVG) or a canvas-based interactive element (fabric.js). This doc
captures the reasoning behind what shipped, since Phase 5 **replaced its own original
plan mid-flight**, twice, as real content and real testing turned up things that
weren't knowable from the roadmap doc alone. Read this before starting whatever's next
— it changes some assumptions the earlier roadmap/Phase 4 notes made.

Commits (in order): `b6c4b9e` (subphase 1: SVG embedding), `4c83429` (subphase 2:
canvas capture, and subphase 3: zero-widget questions, landed together), `b464948`
(canvas-capture quality fixes: tighter crop, higher resolution), `4b5fff3` (removed an
embed-scale factor added in the previous commit, per user feedback).

## 0. The big deviation: adapter interface → two general capabilities

The original roadmap (`2026-08-10 phased implementation roadmap.md`) planned Phase 5/6
as a per-element adapter interface for course-specific static renderers
(`pl-orbitaldiagram`, `pl-lewisstructure`), parsing each element's own `layout_json` or
falling back to `canvas.toSVG()` for core/third-party fabric.js elements like
`pl-drawing`. **This was replaced before any code was written**, at the start of this
session, because:

- Element internals (fabric.js layout JSON shape, canvas structure) are under active
  development in the course repo — an adapter interface tied to today's `layout_json`
  shape would need constant upkeep as those elements change.
- It wouldn't help with SVG/canvas content an instructor embeds directly with no PL
  element involved at all (a real capability gap, not just an implementation detail).

Replaced with two general, element-agnostic capabilities, detection based purely on
`<svg>` tag presence / `.svg` file extension / a configured tag name — never on which
PL element produced the content:
- **SVG embedding** (subphase 1) — rasterize any SVG to a PNG via a headless browser,
  embed like any other image.
- **Canvas capture** (subphase 2) — screenshot a live, authenticated page's canvas
  widget, flatten to a plain image at fetch time.

A third capability (subphase 3, zero-widget questions) turned out to be necessary too,
discovered only once subphase 2 was verified against real content — see §3.

## 1. Subphase 1: SVG embedding (`b6c4b9e`)

New module `svg_render.py`, modeled directly on `latex_math.py`'s pipeline shape
(module-level cache dict, lazy temp cache dir, a typed render-error exception callers
catch and degrade from). Rasterizes via headless Chromium (Playwright) rather than a
pure-Python SVG library (`cairosvg` etc.) — chosen for full CSS/SVG fidelity and
because subphase 2 was already known to need the same headless-browser technology, so
this avoids two separate rendering stacks.

**Corrected mid-session**: the plan initially described this as specific to
`pl-lewisstructure`'s `print="true"` mode. The user pointed out the capability needed
to be general — any raw `<svg>` an instructor embeds directly, or any element's
`.svg`-file `<img>` reference (confirmed via the real PL source:
`<pl-figure>`, a core element, always renders a bare `<img>` regardless of the
referenced file's type, so an SVG used through `<pl-figure>` reaches the page exactly
the same way). The shipped detection (`<svg>` tag presence / `.svg` extension) reflects
this, not the narrower original framing.

**Sizing is measured from the rendered page, not hand-parsed from markup** — the user
flagged that not every SVG an instructor embeds will reliably set `width`/`height`/
`viewBox` the way `pl-lewisstructure`'s confirmed output does. Rather than hand-rolling
a fallback chain matching the CSS/SVG spec, `svg_render.py` loads the SVG into a page
and reads back Playwright's own `locator.bounding_box()` — the browser's real sizing
algorithm, not a reimplementation of it. One real bug found this way during
implementation: an SVG with no explicit size, rendered directly in the page `<body>`
(a block context with a definite width), stretched to the full ~1280px default
viewport width instead of anything related to its own content — CSS `auto` sizing for
an inline `<svg>` resolves as a *percentage* of its containing block, not a fixed
spec default the way `<img>`'s replaced-element sizing algorithm does. Fixed with a
small, fixed fallback viewport (`_FALLBACK_VIEWPORT`, 480×480 CSS px) so this edge case
stays print-reasonable instead of arbitrarily huge; real content with explicit sizing
is unaffected (measures its own true size regardless of viewport).

Verified against real fetched `pl-lewisstructure` output (`lewis-structures-extended`,
`print="true"`) — confirmed the element's real SVG (server-generated by
`chemutils.structures.LewisStructure.render_svg()`) always sets both `viewBox` and
explicit `width`/`height`, consistent with the module's assumptions.

## 2. Subphase 2: canvas capture (`4c83429`, refined in `b464948`/`4b5fff3`)

New module `canvas_capture.py`. Screenshots a canvas-based interactive widget (e.g.
`pl-orbitaldiagram`'s fabric.js canvas, `pl-lewisstructure`'s non-`print` mode) at
**fetch time**, not render time — a canvas's content only exists after real JS
execution against the live variant, so this drives Chromium to the actual
`instance_question` URL with `PLClient`'s authenticated session cookies attached
(`PLClient.playwright_cookies()`, a new method translating `requests.Session`'s cookie
jar into Playwright's `add_cookies()` format), not something replayable from
already-saved static HTML.

**Corrected mid-session (twice)**:
1. The initial plan draft assumed `lewis-structures-extended` (subphase 1's test
   question) would also serve as subphase 2's live-canvas test case. The user
   corrected this: that question has `print="true"` set, so it only ever emits SVG —
   it was never a canvas test case. The user added a new `pl-orbitaldiagram` question
   to the test assessment specifically for this.
2. The plan initially proposed defaulting captured-container failures to "leave the
   raw markup untouched, let it fall through to today's existing unsupported-element
   handling." The user pointed out this would leak stray toolbar button-label text
   into the rendered prompt via `html_parser.py`'s generic-tag walk (which has no
   awareness of these containers). Revised to **guaranteed replacement**: every
   matched container is *always* replaced with an `<img>` before this module returns
   — a real one on success, or an empty-`src` placeholder
   (`alt="[interactive content unavailable]"`) on any failure. This needed zero
   `html_parser.py`/`element_renderer.py` changes at all — `_render_image`'s existing
   fallback already treats a falsy `local_path` as "no file, use alt text."

**Default selector guessing, confirmed against three real fabric.js elements** (not
one): `pl-lewisstructure`, `pl-orbitaldiagram` (both course-authored,
`pl-pitt-chem0110`), and core PL's `pl-drawing`. Findings that shaped the defaults:
- Container class equals the tag name verbatim for both course elements
  (`.pl-lewisstructure`, `.pl-orbitaldiagram`) but **not** for `pl-drawing`
  (`.pl-drawing-container`) — confirms this default can't be universal, hence the
  `container-selector` config override.
- Toolbar class has **no shared suffix convention** across all three
  (`-toolbars`, `-controls`/`-toolbar`, `-sidebar`) — the default hide-selector guess
  tries a fixed candidate list (`_DEFAULT_HIDE_SUFFIXES`) covering all three known
  conventions rather than a single guessed string; non-matching candidates are
  harmless no-ops.

**Quality fixes found reviewing real output** (`b464948`, then partially reverted in
`4b5fff3` per follow-up feedback): the first working capture screenshotted the whole
widget root, which visibly included blank space reserved for the toolbar even after
hiding it via `display:none` — a layout the JS/flex system already sized to
accommodate the toolbar before the hide ran doesn't shrink back retroactively. Also,
captures had no explicit `<img width>` and no extra rasterization resolution, so they
silently fell back to `element_renderer._DEFAULT_IMAGE_WIDTH`'s fixed 3in and looked
low-quality if enlarged. Fixed by:
- Preferring a narrower `.{tag}-canvas-wrap` container selector (confirmed real
  convention in both course elements, wrapping just the `<canvas>`) over the bare
  `.{tag}` root, falling back to the root only if the narrower selector matches
  nothing (`_resolve_container_matches`, tries candidates in order, first match wins —
  distinct from hide-selector guessing, which tries all candidates independently).
- Rendering at 600 DPI (`device_scale_factor`, same mapping `svg_render.py` uses) for
  raster headroom, and setting the replacement `<img>`'s `width` attribute explicitly
  from the captured element's own CSS bounding-box width — previously unset entirely.
- An initial follow-up also applied a 1.25x upscale on top of the natural width; the
  user asked for this to be removed once the crop/resolution issues were fixed, since
  natural size was sufficient on its own (`4b5fff3`).

Verified against real fetched `pl-orbitaldiagram` output: captured PNGs are
3175×2513px (was ~100×60px displayed-resolution before the DPI fix), embed at the
container's natural CSS width with no toolbar whitespace, and the blank vs. key
distinction correctly shows the empty vs. correctly-filled electron-configuration
diagram.

## 3. Subphase 3: zero-widget questions supported (`4c83429`)

**Not originally planned as a separate subphase** — discovered as a direct consequence
of verifying subphase 2 against real content. Both `lewis-structures-extended`
(SVG-only) and the new `pl-orbitaldiagram` question (canvas-only) have no *other*
recognized input widget on the page — subphases 1/2 flatten their diagram to a plain
image, but `html_parser.py`'s `parse_instance_question_html` still raised
`UnsupportedElementError` whenever zero widget groups were found at all, blocking
`pl2docx-render` for the *whole assessment* (not just that one question — a single
`UnsupportedElementError` aborts the whole document render, with no per-question
isolation).

The fix turned out to be very small: `element_renderer.py`'s
`_build_question_contents` already had an `if not question.widgets:` fast path from an
earlier phase (never previously exercised, since nothing before this could produce a
`ParsedQuestion` with zero widgets), and `docx_builder.py` has no widget-count
assumptions anywhere. The only actual blocker was `html_parser.py`'s one explicit
guard. Removed it; `UnsupportedElementError` now only covers the page's generic
containers (`.question-block`/`.question-body`) not being found at all, i.e. the
fetched HTML not looking like a real PL page — not "this specific question type isn't
supported."

Deliberately **did not** add a broader "detect any legitimately-unsupported element
type" heuristic — the risk (some other, still-genuinely-unhandled PL element's raw
markup getting walked generically and leaking garbled text, the same failure mode
subphase 2's guaranteed-replacement fix addresses for canvas elements specifically)
already existed identically for any decorative/unsupported markup sitting *alongside*
a real widget on a page with at least one recognized input, and was never actually
protected against. Scoped exactly to what the user asked for — questions with no
widgets should parse — not invented additional safety nets.

Verified: the full `pl2docx-phase1-test` assessment (all 4 zones, both diagram-only
questions included) renders end-to-end with no regressions to the 3 previously-working
zones (confirmed both before and after, via a temporary structure.json with the
diagram-only zone excluded, to isolate whether other zones still rendered).

## Known limitations / explicitly deferred (not oversights)

- **No per-element adapter interface** — deliberately not built at all; see §0. If a
  future course element needs genuinely bespoke rendering logic beyond
  "screenshot the container"/"embed the SVG," that's still an open problem, not solved
  by this phase.
- **Canvas capture always re-navigates and re-renders live** — no caching across the
  blank/key two-pass fetch (each capture is a fresh authenticated page load). Correct
  given the two panels show genuinely different content (interactive vs. answer state),
  but means fetching an assessment with several interactive-element questions is
  proportionally slower than one with none. Not optimized; no user complaint yet.
- **Toolbar-hiding is display:none, not a layout-aware crop** — for elements whose
  container-selector default doesn't include a `-canvas-wrap`-style tight wrapper
  (i.e. anything falling back to the bare `.{tag}` root, like `pl-drawing` would if
  configured), the same toolbar-reserved-whitespace issue subphase 2's fix addressed
  for the *default* case could still appear, since it's the `-canvas-wrap` selector
  doing the real work, not the hide-selector mechanism. An instructor hitting this
  would need to set an explicit tighter `container-selector` themselves.
- **No config validation for `additional-elements: type: interactive` selectors** —
  a typo'd `container-selector`/`hide-selectors` string fails silently per-question
  (falls to the placeholder image, logged as a warning) rather than failing the whole
  run the way a missing declared LaTeX package does (`latex_math.py`'s
  `LatexPackageNotFoundError`). Consistent with `SvgRenderError`'s per-item philosophy,
  but worth knowing: a systematically wrong selector produces N silent placeholders,
  not one loud error.

## Testing patterns established this phase

- **Local HTTP server fixture for browser-driven tests**: `test_canvas_capture.py`
  serves a small static HTML fixture (fake widget + canvas + toolbar) over a real
  local `http.server.ThreadingHTTPServer` in a background thread, rather than hitting
  the actual PL dev server — keeps Chromium-dependent tests offline/CI-safe while
  still exercising a real browser navigation + screenshot round-trip. Reused a
  factory-fixture shape (`start_server(html) -> url`) so multiple distinct pages can
  be served within one test.
- **Height/width as a behavioral proxy for "did hiding/cropping actually work"** —
  rather than pixel-diffing images, tests assert relative PNG dimensions (e.g. a
  hidden-toolbar capture is shorter than the same capture without hiding) as a cheap,
  robust check that doesn't require exact-pixel golden-image fixtures.
- **Shared `chromium_available()` helper** (`conftest.py`, added in subphase 1,
  reused here) — a cached, real-launch-attempt check, mirroring
  `test_latex_math.py`'s `shutil.which`-based skip but for a browser rather than a
  PATH binary.
